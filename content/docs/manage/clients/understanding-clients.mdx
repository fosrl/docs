A client is a way to access resources on sites remotely and privately via a virtual private network. Clients are used with private resources to faciliate zero-trust network access.

By default a client does not have access to any hosts on the local network of the site. Admins must explicitly define resources on the site and give specific users and roles access to the resources.

Users must log in and connect from a Pangolin client available on [Windows, Mac, Linux, iOS/iPadOS, and Android](/manage/clients/platforms). They sign in with their user credentials through a web login flow. Machines (automated systems and servers) connect with [machine client credentials](/manage/clients/machine-clients#credentials): an ID, secret, and endpoint.

## Client Types

There are two types of clients: user devices and machines.

### User Devices

A user may download a client for their specific system. Before they can connect, they select a Pangolin server and log in with their user credentials through the web login flow. Users can log in as a Pangolin user or with your attached external identity provider.

Examples include:

- **SSH**: Admins and developers can connect with their client to specific hosts for SSH.
- **RDP**: Users can connect to a remote host using familiar remote desktop software.

Then, just like in the Pangolin dashboard, a user selects the organization to connect to. Once connected, all resources made available to the user in that organization become available via the tunnel.

#### How User Devices Authenticate

Under the hood, each user device is given an ID and secret, similar to a [machine client](/manage/clients/machine-clients#credentials). The difference is that for a user device, the secret is **not** what authenticates the connection, so the same ID and secret are reused across logins. This is intentional and is not a security flaw.

Instead, every user device must present a valid **user session token**, which the client gets through the login flow in the client app. That session must belong to the same user the device is registered to. When the user logs out, the session is invalidated, and a new one is issued the next time they log in. The device's ID and secret stay the same.

Pangolin also recognizes user devices by their [fingerprint](/manage/clients/fingerprinting#how-devices-are-recognized), so reinstalling the client on the same device shows it as the same device in the dashboard. Any [block](/manage/clients/archiving-blocking#blocking-devices) on it stays in effect.

| | User devices | Machine clients |
|---|---|---|
| ID and secret | Yes, reused across logins | Yes |
| What authenticates the connection | A user session token from the login flow, bound to the device's user | The ID and secret |
| Logging out | Invalidates the session; the ID and secret are unchanged | Not applicable |

### Machines

Machine clients are for servers and automated systems that are not associated with a specific user.

Examples include:

- **CICD**: Access remote resources like a database in an automated deployment pipeline.
- **Servers**: Provide a VPS with access to a resource running in a different network.

Though you may connect a server via a user account using a CLI client, we recommend you specifically use a machine client.

Machine clients authenticate with [machine client credentials](/manage/clients/machine-clients#credentials): an ID and secret. These are passed as arguments to the Pangolin CLI. They can be revoked and rotated. For machine clients, the secret is the authentication mechanism, because there is no user session. You can also assign [roles](/manage/clients/machine-clients#grant-access-to-private-resources) to a machine client so it inherits private-resource access from those roles.

## Split Tunneling by Default

Pangolin clients are split tunnel by default. The client only sends traffic for the private resources a user or machine can access through the tunnel. That includes resource IPs, CIDR ranges, and [aliases](/manage/resources/private/alias). Everything else, such as public websites, video calls, and devices on the local network like printers, stays on the device's normal internet connection. This keeps regular browsing fast and avoids sending traffic through your sites that doesn't need to go there.

DNS is split too. With [Override DNS](/manage/clients/dns#override-dns-enable-aliases) on, the client answers names for your Pangolin resources and forwards every other lookup to an upstream DNS server over the normal connection. DNS only goes through the tunnel if you turn on [DNS Over Tunnel](/manage/clients/dns#dns-over-tunnel). See [DNS](/manage/clients/dns).

To route **all** traffic through Pangolin like a traditional full-tunnel VPN, set up an [exit node](/manage/resources/private/exit-node). An exit node resource sends the default routes (`0.0.0.0/0`) through a site, so internet traffic leaves from that site's network. Even then, other private resources keep working through their own sites unless you turn on [Exit Nodes Take Precedence Over Resources](/manage/clients/platforms#exit-nodes-take-precedence-over-resources).

## Client Modalities

Clients connect to sites over the same local network, with NAT hole punching, or by relaying. When a client and site share a local network, they connect directly over the LAN and the traffic never leaves it. Otherwise the client attempts a direct peer-to-peer tunnel through NAT, then falls back to relaying through your Pangolin server if hole punching fails. Same-network detection requires Pangolin 1.21 or later clients and sites.

See [NAT Traversal](/manage/clients/nat-traversal) for how each modality works, how to check whether a site is local, direct, or relayed, and tips for improving hole punching reliability.

### How Traffic Leaves the Site

The site connector (Newt or the Pangolin CLI) runs in userspace and terminates the WireGuard tunnel from the client. To reach resources on the site's local network, it applies source NAT (SNAT) to client traffic. Resources see connections coming from the site connector's IP address, not the client's.

Without SNAT, packets would carry the client's WireGuard tunnel IP. Hosts on the site network have no route back to that address, so replies would never reach the client.

Keep this in mind when troubleshooting connectivity or writing firewall rules on the site network: allow traffic from the site connector's host, not from client tunnel IPs.
